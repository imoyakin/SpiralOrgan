# 设计
总体来看，就是为了实现目标的拼脑花中枢
目标： 本软件的目标是实现合理的，AI群控技术,通过具体的公示目标，完成目标的执行。  
功能：   

* 执行脚本，编写代码，并生成对应记忆 （通过skill限制）
* 读取屏幕，识别文字，按照kanban或者记忆要求，编辑文本和执行点击，并生成对应记忆
* 记忆被通过向量的形式存储的同时，留下文字或者文字配图说明文档（markdown）和vector一并保存，并留下合适标题
* 记忆可被打tag方便检索
* 记忆可被通过flutter ui进行展示
* 记忆可被评分，或者被用户点赞或者点踩（针对记忆内容本身）
* 可以读取多个目录，同时管理多个项目放到一个大的kanban上下文（因为我有多个项目要同时开发互相配合）
* 每次执行功能前，读取记忆寻找可复用记忆，每次context上下文可以复用多个记忆，记忆内容依照用户的评分，在执行的时候，根据正面或者负面的评分，影响行为（比如开启使用`rm -rf`相关的负面记忆，让模型倾向于不执行这个命令）
* 用户可以在特定的会话中（类似project或者target）中，设置记忆白名单，记忆黑名单（影响到框架对记忆是否读取）
* 有全局默认开启记忆，用户可以随时拖拽进来或者拖拽出去
* 记忆可被用户分享给其他用户（现在不做，长期需求），分享后，在大家平分的网站上，其他用户只能点赞。这就意味着每个记忆都有uuid
* 每次编写代码和执行脚本，最好能在一个独立的容器中操作（后续实现，暂缓）
* 可以按照设定的`ghost.md`，调用agent，提供和用户互动的桌宠能力（后续实现，暂缓）
* 用户可以像是设计pipeline一样，随意定义
* 可以接入rss订阅，读取新闻，根据
* 像是openclaw一样连接聊telegram，在ui管理连接的telegram
  * 连接telegram后，可以构筑一个角色，通过编辑markdown `ghost.md` 来实现，使用google的a2a机制
  * 这个telegram会在ui上显示跟他互动过的用户
  * 这个telegram可以设置白名单id，这个白名单id可以选择，从互动过中的用户沟通
  * 只有白名单的用户，可以执行高权限操作，其他用户只能按照限定的频率调侃聊天，且会针对每个用户构建单独的记忆
  * 不同用户私聊交互，不能访问其他用户的记忆。一个群组中的沟通，会设定为一个群组的共通记忆。
  * 
* 支持多个ai provider，且可以跟具体的`ghost.md`配置亲和属性
* `ghost.md`是必须载入的
* 有插件市场
* 记忆目前考虑是否可以提炼为lora（暂时不做）

核心业务逻辑：
有一个核心的大的kanban
针对某个具体的项目，每次执行工作前，先分析用户需求，编辑todo，在用户确认后，编写一个看板记忆针对这个项目（或者同时留下markdown说明）
针对具体的需求，拆分需求到细则。
启动多个worker agent，分细则执行。同时，监视kanban的agent可以开启新的supervision agent，审查其工作是否完成。
每个任务，worker和supervision agent都会和事实对齐：比如编码任务，通过编译并执行检查是否执行了符合预期的逻辑，抑或是编译执行，如果软件需要观察图片或者录音审查，则申请对应的权限然后继续工作，通过支持vision的agent继续审查。如果无法和事实对齐，可以提问用户，通过暂停等待用户的互动，或者用户同意持续自动工作后，一直持续工作到kanban的todo完成。
用户随时可以中断，中断的时候，放下手头工作，完善文档，或者暂停业务。这个时候用户的需求可能是关机或者检查工作状态和具体的实现。
核心业务逻辑中，可以给agent配置`ghost.md`。这个`ghost.md`可能会有很多个，这个能从插件市场下载，也可以用户自己创建，每个ghost和其memory单独使用一个文件夹，名称为了防止重复使用uuid，在ghost标题中编写其具体的名字，可以有文字描述，也可以在```code的形式中，直接嵌入向量，并配有说明

进度：计划已建立并完成初步任务。接下来列出角色并描述交互。以下为详细论述。

主要角色与职责

甲方/业主 (Owner): 出资方，确定项目需求、验收标准、批准变更、付款；最终接受工程并接收移交资料。
业主代表/项目经理 (Owner PM): 代表甲方日常决策、审批、验收及合同管理接口。
设计方/咨询 (Designer / Consultant): 提供设计图纸、技术说明、变更设计与答疑（RFI 回应）。
施工总承包方 (Main Contractor): 负责施工组织、分包管理、进度与质量保证、施工报告、申请付款。
分包商 (Subcontractors): 专业工程执行（结构、机电、装饰等），受总承包管理。
监理/监造 (Supervisor / Clerk of Works / PMC): 代表业主进行质量、安全、进度监督、检验并出具验收证书/报告。
造价/投资控制 (QS / Cost Manager): 招投标、索赔/签证、支付款项核算与成本控制。
安全/环境经理 (HSE Officer): 现场安全与环保检查、事故报告和整改跟踪。
材料/设备供应商 (Suppliers / Vendors): 供货、出具质保与合格证明、交付记录。
试验检测机构 (Testing Labs): 材料/构件检测并提交检测报告。
政府/监管机构 (Authority / Inspectorate): 审批许可、验收、合规检查。
出资方/金融方 (Lender / Financier): 放款、进度款与合规性审查（若有）。
保险方 (Insurer): 承保工程险/责任险，事故理赔接口。
运营/维护方 (Operator / FM): 接收竣工资料并承担后期运维。
公众/权利相关方 (Stakeholders / Public): 道路占用、邻里沟通、征地拆迁等（视项目而定）。

各角色之间的典型交互方式

合同与权限路径：甲方 ↔（合同）↔ 施工方；甲方 ↔（委托）↔ 监理；甲方 ↔（委托）↔ 设计方。合同定义责任、付款条件、变更程序与争议解决。
沟通渠道：正式文档（合同、图纸、签证）、会议（周例会/月例会）、现场通知单、电子系统（RFI、变更单、进度表）、移动端日报/验收单。
审批链：施工方提交申请（付款申请、变更申请、试验报告），监理审核（或驳回），甲方/造价复核并批准或拒绝，财务执行付款。
质量与检验：施工方自检 → 监理/第三方检测 → 合格放行或整改 → 最终部分/阶段性验收（带签字章/证书）。
变更与索赔管理：施工方提出变更/签证 → 提交成本与进度影响评估 → 监理/设计审核 → 甲方批准并变更合同价/工期 → 更新进度与付款。
安全/事件流程：事故上报 → 现场隔离 → 调查（监理/甲方/第三方）→ 整改措施下发 → 完成闭环。
交付与移交：逐项验收清单 → 缺陷登记并整改 → 竣工验收合格书 → 提交竣工文件包（竣工图、试验报告、质保书、操作手册）→ 移交给运维方。
关键工作流举例（含文档与状态）

RFI（设计/现场技术询问）流程
发起：施工方创建 RFI（描述、影响、建议）
审核：监理初审 → 设计方或业主技术负责人解答
结果：接受/拒绝/补充信息；结果挂钩到变更或施工指令。
变更单（Change Order / Variation）流程
提交变更申请（原因、费用、工期影响）
监理/设计成本与技术评估 → 甲方审批 → 签署合同变更 → 更新预算与进度。
付款申请（Progress Payment）流程
施工方提交支付申请（进度量/发票/质保）
监理核验进度与质量 → 造价审核 → 甲方/财务付款 → 留存凭证。
检验与放行（Inspection）
检验申请 → 监理/第三方检测 → 合格/不合格 → 若不合格，生成整改任务并闭环。
竣工移交流程
逐项验收 → 竣工图与文件提交 → 业主验收并签字 → 质保期启动。

工作流引擎：支持可配置审批流（多级审批、并行/串行）、超时提醒、强制附件与审批条件。
事件/通知：事件总线（Webhooks/消息队列）用于实时通知（手机推送/邮件/SMS），并可与外部 ERP/财务同步。
移动优先：现场人员能离线记录巡检、拍照、RFI、签名，回网上传合并并触发工作流。
BIM 与图纸管理：支持图纸版本控制、图纸标注（与 RFI/检验项挂钩）、3D 模型（BIM）指向构件的工单与检验记录。
集成点：财务/ERP（付款与发票）、供应链（采购/交付）、HR/考勤（劳务记录）、政府审批接口、传感器/物联网（进度/桩基/环境监测）。
合规与证据链：试验报告、照片、视频、位置信息与签名作为变更/索赔/理赔证据。
具体工作流实现细节（示例）

RFI 表模型要含字段：id, project_id, raised_by (party_id), raised_at, location(ref to BIM), description, proposed_solution, severity, related_contract_items[], attachments[], status, assigned_to (designer_id), response_by, response_at, linked_change_order_id。

交互样例序列（简化）

日常：施工方上传 DailyProgress → 监理审核并评论 → 业主查看仪表盘 → 财务基于已核实进度触发分期付款。
